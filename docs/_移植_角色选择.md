> **基于**: `_分析_角色选择系统.md` 的 dnfile 元数据分析
> **产出日期**: 2026-09-23
> **原则**: 本文件是**移植方案文档**，不实际修改 DLL。原文件备份在 `_backup/Assembly-CSharp.dll.orig`。

## 1. 概述

### 1.1 移植范围

将 Godot 侧 5 角色的定义（属性倍率 + 必杀技 + 隐藏解锁）移植到 Unity 原版 `Assembly-CSharp.dll` 及关联数据文件中。

### 1.2 关键架构发现

通过 dnfile 分析确认：

| 数据类型 | 存储位置 | DLL 可改？ |
|---|---|---|
| 类/方法/字段元数据 | DLL 内（TypeDef/MethodDef/FieldDef 表） | ✅ 可改 |
| 方法体 IL 逻辑 | DLL 内（MethodDef RVA → IL 字节码） | ✅ 可改 |
| 常量值（enum 等） | DLL 内（Constant 表） | ✅ 可改 |
| **角色属性数据**（hp/speed/punch 等数值） | **外部 AssetBundle**（`StreamingAssets/aa/` 下的 `.bundle` 文件） | ❌ DLL 不含运行时数据 |
| **必杀技分配**（ewazaid1-5） | **外部 AssetBundle**（mstFodd_CharaData ScriptableObject） | ❌ DLL 不含运行时数据 |
| **角色解锁状态** | 存档文件（CSaveData）+ 运行时 CharaSelectInfo.isOpen | ⚠️ 逻辑可改，初始值需配合 |

> **核心结论**: `mstFodd_CharaData.dataArray` 是实例字段（非 static/literal），说明数据从 Addressables 加载。DLL 只定义了"数据结构"，不包含"数据值"。因此移植分两条线：
> - **DLL 补丁线**: 修改方法逻辑（解锁条件、属性覆盖、必杀技触发）
> - **AssetBundle 线**: 修改 ScriptableObject 数据（属性数值、waza 分配）

### 1.3 移植策略

采用 **DLL 运行时覆盖** 为主方案：在 DLL 中 patch 关键方法，使其在运行时用 Godot 定义的数值覆盖从 AssetBundle 加载的原始数据。这样不需要解包/重打包 AssetBundle，降低风险。

## 3. 属性倍率对齐方案

### 3.1 atk_mult → punch_mul / kick_mul / weapon_mul

Unity 原版有三套独立攻击倍率（拳击/踢击/武器），Godot 合并为单一 `atk_mult`。

**方案**: 统一乘同一系数，三套倍率相同：

```
punch_mul = atk_mult
kick_mul  = atk_mult
weapon_mul = atk_mult
```

### 3.2 jump_mult 和 melee_range_mult 的处理

Unity 侧 `mstStatusTableData` 没有 jump 和 melee_range 字段。

**jump_mult 方案**: Unity 用物理参数 `gravity` 和 `jump_velocity` 控制跳跃。在 `CharaStatus` 或玩家控制器中，将 `jump_mult` 作为跳跃速度倍率应用：
- `jump_velocity_final = base_jump_velocity * jump_mult`
- 这需要 patch 玩家控制器的跳跃方法，或在 `CharaStatus` 中新增字段

**melee_range_mult 方案**: Unity 用 `damagecollision`（伤害碰撞体尺寸）控制攻击范围。在运行时按倍率缩放 hitbox：
- `hitbox_size_final = base_hitbox_size * melee_range_mult`
- 这需要 patch 攻击判定方法，或在 `CharaStatus` 中新增字段

### 3.3 每角色完整目标值表

## 4. 必杀技槽位对齐方案

### 4.1 槽位分配

Unity 每角色有 5 个 waza 槽位（`ewazaid1-5` + `iswaza1-5special`）。Godot 每角色 1 个必杀技。

**方案**: 将 Godot 的 `special_skill` 写入 **槽位 1**（`ewazaid1`），并设置 `iswaza1special = true`。其余 4 个槽位保持原值（或清空为 `NONE`）。

| 槽位 | 处理方式 |
|---|---|
| `ewazaid1` / `iswaza1special` | **写入 Godot special_skill，标记为 special** |
| `ewazaid2` / `iswaza2special` | 保持原值（或设为 NONE/false） |
| `ewazaid3` / `iswaza3special` | 保持原值（或设为 NONE/false） |
| `ewazaid4` / `iswaza4special` | 保持原值（或设为 NONE/false） |
| `ewazaid5` / `iswaza5special` | 保持原值（或设为 NONE/false） |

### 4.2 5 角色必杀技写入表

| 角色 | ewazaid1 | iswaza1special | ewazaid2-5 | iswaza2-5special |
|---|---|---|---|---|
| pompadour (KUNIO) | `WAZA2_M_KICK` (19) | true | 保持原值 | 保持原值 |
| fighter (RIKI) | `WAZA2_M_PUNCH` (1) | true | 保持原值 | 保持原值 |
| sprinter (SUGATA) | `WAZA2_SENPU_KICK` (25) | true | 保持原值 | 保持原值 |
| tank (GOUDA) | `WAZA2_STOMPING` (58) | true | 保持原值 | 保持原值 |
| bosozoku (ONIZUKA) | `WAZA2_NINGEN_DORIL` (18) | true | 保持原值 | 保持原值 |

### 4.3 实现方式

由于 waza 数据在 AssetBundle 中（不在 DLL 中），有两种实现路径：

**路径 A — AssetBundle 修改（推荐）**:
- 用 UnityPy 解包 `nk21_chara_player_assets_all.bundle`
- 找到 `mstFodd_CharaData` ScriptableObject
- 修改对应角色行的 `ewazaid1` 和 `iswaza1special`
- 重新打包

**路径 B — DLL 运行时覆盖**:
- patch `mstFodd_CharaDataData` 的属性 getter（如 `get_eWazaID1()`）
- 在 getter 中按角色 ID 返回 Godot 定义的 waza 值
- 这样不需要改 AssetBundle

## 5. 隐藏角色解锁方案

### 5.1 当前 Unity 原版解锁机制

从 dnfile 分析确认：

| 组件 | 位置 | 作用 |
|---|---|---|
| `CharaSelectInfo.isOpen` | 字段 (bool) | 每个角色槽位是否解锁 |
| `CTenchiCharaSelectMenu.IsScelectedCharaOpen()` | 方法 | 检查角色是否解锁 |
| `CTenchiCharaSelectMenu.get_UseCharacterOpenValue()` | 方法 | 从存档读取解锁进度 |
| `CTenchiCharaSelectMenu.SetPlayerUseCharacterOpen()` | 方法 | 设置角色解锁状态 |
| `m_SpriteGrayscaleMaterial` | 字段 | 未解锁角色灰度材质 |
| `m_NotOpenSprite` | 字段 | 未解锁角色占位图 |
| `CSaveData` | 类 | 存档数据（含 m_IsOpenYamadaMode 等解锁标记） |

### 5.2 暴走族（ONIZUKA）改为隐藏角色

**目标**: ONIZUKA 默认锁定，通关第一章后解锁。

**方案**:

1. **初始锁定**: patch `CTenchiCharaSelectMenu.Initialize()` 或 `Open()` 方法，在初始化角色列表时，将 ONIZUKA（EnumCharacterID = 6）的 `isOpen` 设为 `false`。

2. **解锁条件**: 通关第一章 = Story Save Data 中某个 flag 被设置。Unity 侧有 `CFlag` 类（Set/Clear/Is 方法）和 `CSaveData.m_StoryParamArr`。

3. **解锁检查**: patch `IsScelectedCharaOpen(EnumCharacterID, int)` 方法：
   - 如果角色是 ONIZUKA（6），检查存档中第一章通关 flag
   - 如果已通关 → 返回 true
   - 如果未通关 → 返回 false（显示灰度+占位图）

### 5.3 存档 flag 映射

Godot 侧用 `Achievements.is_unlocked("clear_ch1")` 检查通关第一章。Unity 侧对应的是 `CSaveData` 中的 story progress flag。

从 dnfile 分析确认 `CSaveData` 有 `m_StoryParamArr`（故事参数数组）和 `m_StoryParamIndex`。具体哪个 flag 对应"第一章通关"需要运行时调试确认，但方案是：

```
IsScelectedCharaOpen(ONIZUKA, player) 
  → if story_progress >= CHAPTER_1_CLEAR_FLAG
      return true
    else
      return false
```

### 5.4 解锁后的视觉反馈

Unity 原版已有完整机制（灰度材质 + 占位图 + 解锁标签），patch 后自动生效，无需额外开发。

    }

    // 辅助：按类名+方法名查找方法
    static MethodDef FindMethod(ModuleDef module, string className, string methodName)
    {
        foreach (var type in module.GetTypes())
        {
            if (type.Name == className)
            {
                foreach (var method in type.Methods)
                {
                    if (method.Name == methodName)
                        return method;
                }
            }
        }
        return null;
    }

    // 辅助：按类名查找类型
    static TypeDef FindType(ModuleDef module, string className)
    {
        foreach (var type in module.GetTypes())
        {
            if (type.Name == className)
                return type;
        }
        return null;
    }
}

## 7. 风险和注意事项

### 7.1 DLL 修改风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| IL 注入导致方法栈不平衡 | DLL 崩溃/游戏无法启动 | 在测试机上先运行验证；保留原 DLL 备份 |
| 修改方法签名 | 破坏 Unity 序列化兼容性 | 不修改已有方法签名，只修改方法体内部逻辑 |
| 新增字段 | Unity 序列化数据不匹配 | 新增字段用 `[NonSerialized]` 或放在辅助类中 |
| 多版本冲突 | 其他依赖该方法的代码行为异常 | 只在特定分支（特定角色 ID）覆盖，默认走原始逻辑 |

### 7.2 AssetBundle 修改风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| UnityPy 解包失败 | 数据丢失 | 先备份原始 .bundle 文件 |
| 重打包后 Addressables 路径变化 | 游戏找不到资源 | 保持 bundle 路径和 hash 不变，或同时修改 catalog |
| ScriptableObject 类型匹配 | 反序列化失败 | 确保 UnityPy 的类型映射与 Unity 版本一致 |

### 7.3 推荐执行顺序

1. **先做 DLL 补丁线**（运行时覆盖）：不改 AssetBundle，风险最低
