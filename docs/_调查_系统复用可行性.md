# 热血物语：末日丧尸 — Unity 原版系统复用可行性调查报告

> 调查对象：River City Rival Showdown（Unity 原版，C# 编译 DLL）
> 目标项目：hot-blood-zombie（Godot 4.3，GDScript）
> 调查日期：2026-09-22
> 调查方式：只读，使用 `strings` + `dnfile` 解析 .NET 元数据 + 逐文件阅读 Godot 脚本
> 约束：未修改任何工程文件，未安装大型反编译器

---

## 一、结论先行

**可以复用，但不是"搬代码"，而是"搬设计 + 搬数据结构 + 搬数值表"。**

原游戏的核心逻辑是典型的 **MonoBehaviour + 状态机 + ScriptableObject 数据表** 架构，没有引擎专属黑盒，系统划分清晰，类名/字段名/方法名全部可通过 dnfile 从 DLL 中精确读出（2051 个类型、20761 个字段）。但以下内容**不能直接搬**：

- **Animator 状态机**（839 个动作状态 + 3068 个动画枚举绑定在 Unity AnimationClip 上）
- **UGUI Canvas / 事件系统**（所有 UI 类继承 MonoBehaviour，依赖 Unity UI 框架）
- **NavMesh 导航**（UnityEngine.AI，Godot 需用 NavigationServer2D 重写）
- **Addressables 资源加载**（异步资源管理，Godot 用 ResourceLoader/预加载）
- **Fungus + Lua 对话系统**（202 方法的 Lua 桥接，需评估替代方案）
- **联机 P2P + Steam 房间 + 排行榜**（复杂度高，单机项目可跳过）

Godot 项目已经有一套**完整可玩的数值与机制闭环**（26 个脚本、约 7850 行），战斗/武器/经济/商店/成就/敌人AI/Boss/关卡/触控均已实现。因此最优策略是：**以 Godot 现有实现为骨架，用 Unity 版的系统设计和数据表来"填肉"和"对齐"**，而不是从零翻译 C# 代码。

### 2.3 调查方法与证据深度

| 方法 | 结果 | 证据等级 |
|---|---|---|
| `strings`（ASCII + UTF-16LE） | ✅ 成功，提取类名/字符串常量 | 中（可能有误报） |
| `dnfile` 解析 .NET 元数据 | ✅ **主力方法**，精确读出 TypeDef/FieldDef/MethodDef | **高（100% 确定）** |
| `pefile` | ✅ 安装成功，辅助验证 PE 结构 | 高 |
| `monodis` / `ikdasm` | ❌ 环境未安装 | — |
| ILSpy / dnSpy | ❌ 按约束未安装（大型GUI） | — |

> **本报告中所有类名、字段名、方法名、枚举成员名均来自 dnfile 直接解析 .NET 元数据表，属于确定事实。** 唯一不确定的是**具体数值字面量**（HP、伤害、价格等）——它们编译在 ScriptableObject 资源（.asset）中，经 Addressables 运行时加载，不在 Managed/ DLL 内。

## 六、角色选择系统专项判断

### 6.1 原游戏选人系统结构

Unity 版有**两套选人系统**：
1. **故事模式** `CTenchiCharaSelectMenu`：选主角（国夫/力），含生命数(UpdateLifeCount)、友军伤害(UpdateFriendryFire)设置
2. **对战模式** `CFoDDCharaSelect`：支持单人/离线对战/在线对战，每角色5个必杀技槽位

核心数据结构 `mstFodd_CharaDataData`：
```
id, echaraid(角色ID), charaicon(图标), charaname1p, charaname2p,
ewazaid1..5(必杀技ID×5), iswaza1special..5(是否特殊技×5)
```

### 6.2 Godot 现有选人系统

`character_data.gd` 的 `CHARACTERS` 字典：
```
key → {name, desc, color, speed_mult, atk_mult, hp_mult, jump_mult,
       melee_range_mult, special_skill, special_damage, hidden}
```

5名角色：pompadour(飞机头主角) / fighter(格斗专家) / sprinter(疾风飞毛腿) / tank(铁壁壮汉) / bosozoku(暴走族总长，隐藏)

### 6.3 映射与适配判断

| 对比项 | Unity 版 | Godot 版 | 适配建议 |
|---|---|---|---|
| 角色数量 | 对战模式待定（数据表在资源中），主角国夫+力 | 5名 | 保持5名，做命名映射 |
| 属性模型 | 基础值(hp/sp/punch/kick/speed/tough/luck) + 成长表 + 状态倍率 | 倍率制(×基础值) | **扩展为基础值+倍率**，对齐 `mstActorParamaterData` |
| 必杀技 | 每角色5槽，标记是否特殊技 | 每角色1个 | **扩展为5槽**，对齐 `ewazaid1..5` |

### 7.3 关键风险提示

1. **数值数据不在 DLL 中**：具体 HP/伤害/价格/掉落率等数值在 ScriptableObject 资源（.asset）中，经 Addressables 加载。如需精确对齐数值，需另行从游戏数据目录提取 .asset 文件或用 Unity 打开工程导出。
2. **动画状态量巨大**：839 个动作状态 + 3068 个动画枚举，完整复刻需要大量美术资源和动画制作，不是代码工作量。
3. **Lua 对话系统不可直接迁移**：202 方法的 Lua 管理器与 Fungus 框架深度绑定，Godot 端需用原生方案重写。
4. **Godot 现有代码已可玩**：不要为了"复刻"而推翻已有实现。最优策略是增量扩展，不是重写。
5. **另一个 UI 复刻子代理正在进行**：立绘/贴图接入工作并行，角色选择系统的改动需与其协调。
